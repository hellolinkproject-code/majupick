# WorkBridge

의뢰인과 프리랜서를 연결하는 프로젝트 중개 플랫폼 (코드잇 풀스택 JavaScript 과제).

> 현재 단계: **AI 단가 분석 기초(STEP 08-A, `AI_ESTIMATE_MODE=mock`)**. 이메일 회원가입·로그인(STEP 04-A), Google 로그인·역할 선택(STEP 04-B), 역할별 프로필(STEP 04-B-2), 프로젝트 등록·관리(STEP 05-A), 프로젝트 검색·필터·정렬(STEP 05-B), 사용자 공개 프로필(STEP 05-C), 프리랜서 프로젝트 지원(STEP 06-A), 의뢰인 지원자 관리·선정·거절(STEP 06-B), 인앱 알림·모집 마감(STEP 06-C), 북마크·추천(STEP 07-A), 프로젝트 취소·역할별 헤더(STEP 07-B)도 그대로 동작한다. 기본 필수 요구사항별 상태는 `planning/ACCEPTANCE_MATRIX.md` §6. 화면은 홈·로그인·회원가입·Google 완료·계정 연결·역할 선택·내 프로필(의뢰인/프리랜서 프로필 편집, 프로필 이미지)·공개 프로필·프로젝트 찾기·프로젝트 등록(3단계, 2단계에서 AI 단가 분석·예산 반영)·프로젝트 상세(지원, 북마크, 추천 프로젝트, 소유자용 지원자 관리·모집 마감 포함)·수정(AI 단가 분석 포함)·내 프로젝트·내 지원 현황·내 북마크·알림·404. 로컬 PostgreSQL에 사용자·프로필·기술 스택·프로젝트·지원·알림·북마크·OAuth 상태 테이블이 있다. 실제 OpenAI 연동·계약·전자 서명·결제는 이후 단계다.
> 기획·설계 문서는 [`planning/`](./planning)에 있다.

```text
workbridge/
├─ apps/
│  ├─ api/            # Express API 서버 (src/app.js, src/server.js, test/)
│  │  ├─ prisma/      # DB 스키마(schema.prisma)와 마이그레이션 SQL
│  │  └─ scripts/     # 로컬 DB 준비·점검 스크립트
│  └─ web/            # React + Vite 앱 (src/app, pages, components, lib, stores)

├─ eslint.config.js
└─ package.json       # npm workspaces 루트
```

## 시작하기

필요 환경: Node.js 22.22.2 이상(권장 26), npm 10 이상, PostgreSQL 18(로컬 설치)

```bash
npm install
npm run db:generate -w apps/api   # Prisma Client 코드 생성 (처음 한 번, 스키마가 바뀔 때마다)
npm run dev
```

`.env`가 없으면 아래 [데이터베이스](#데이터베이스-로컬-postgresql) 절차를 먼저 진행한다. DB 없이 화면만 볼 때는 `Copy-Item .env.example .env`로 복사해도 되지만, 이 경우 DB 기능은 동작하지 않는다.

- 프론트엔드: <http://localhost:5173>
- 백엔드 상태 확인: <http://localhost:4000/api/health>
- 개발 중 프론트엔드의 `/api/*` 요청은 Vite가 백엔드로 프록시한다.

루트의 `.env` 하나를 백엔드와 프론트엔드가 함께 읽는다. 프론트엔드에는 `VITE_`로 시작하는 변수만 노출되므로 비밀 값에는 `VITE_`를 붙이지 않는다. `.env`는 커밋하지 않는다.

## 데이터베이스 (로컬 PostgreSQL)

WorkBridge는 내 PC에 설치된 PostgreSQL 18을 쓴다. 용도별로 DB 3개를 나눠 쓰고, 모두 WorkBridge 전용 계정 `workbridge_app`이 소유한다. 이 계정에는 관리자 권한이 없다.

| DB                  | 용도                                                | `.env` 변수           |
| ------------------- | --------------------------------------------------- | --------------------- |
| `workbridge_dev`    | 개발 서버(`npm run dev`)가 쓰는 DB                  | `DATABASE_URL`        |
| `workbridge_test`   | 자동 테스트(`npm run test:db`) 전용                 | `TEST_DATABASE_URL`   |
| `workbridge_shadow` | Prisma가 마이그레이션 파일을 만들 때만 잠시 쓰는 DB | `SHADOW_DATABASE_URL` |

### 1. DB 준비 (처음 한 번)

1. PostgreSQL 관리자(`postgres`) 비밀번호를 알고 있어야 한다. 잊었다면 [`apps/api/scripts/POSTGRES_RECOVERY.md`](./apps/api/scripts/POSTGRES_RECOVERY.md)를 본다.
2. PowerShell에서 아래 스크립트를 실행한다. 비밀번호는 화면에 보이지 않는 입력 창에서 직접 입력한다. 계정·DB 3개를 만들고 루트 `.env`에 접속 정보를 저장한다. 이미 있는 DB는 지우지 않는다.

   ```powershell
   powershell -ExecutionPolicy Bypass -File apps/api/scripts/setup-local-db.ps1
   ```

3. 연결을 확인한다. 세 DB 모두 `✔`, `superuser=false`, `TimeZone=UTC`가 나와야 한다.

   ```bash
   npm run db:check -w apps/api
   ```

### 2. 마이그레이션 (테이블 만들기)

마이그레이션 파일은 `apps/api/prisma/migrations/`에 있다. 새로 받은 마이그레이션을 내 DB에 적용할 때는 아래 두 명령을 실행한다. 기존 데이터를 지우지 않고, 아직 적용하지 않은 파일만 순서대로 적용한다.

```bash
npm run db:migrate:deploy -w apps/api   # 개발 DB
npm run db:migrate:test -w apps/api     # 테스트 DB
npm run db:migrate:status -w apps/api   # 개발 DB 적용 상태 확인
npm run db:seed:tech-stacks -w apps/api # 기본 기술 스택 27개(여러 번 실행해도 같음)
```

`db:seed:tech-stacks`는 기술 스택 기본 선택지만 넣는다. 사용자·프로젝트 같은 더미 데이터는 넣지 않고, 이미 있는 행은 바꾸지 않는다. 테스트 DB에 넣을 때는 `npm run db:seed:tech-stacks -w apps/api -- --test`.

스키마(`schema.prisma`)를 바꿔 새 마이그레이션을 만들 때는 다음 순서를 따른다.

1. `npm run db:validate -w apps/api`: 스키마 문법 검사
2. `npm run db:migrate:create -w apps/api -- --name <변경_이름>`: SQL 파일만 만들고 적용하지 않음
3. 생성된 `migration.sql`을 열어 `DROP`·`TRUNCATE`·컬럼 삭제가 없는지 확인
4. 위의 `db:migrate:deploy`, `db:migrate:test`로 적용
5. `npm run db:generate -w apps/api`: Prisma Client 다시 생성

> `prisma migrate reset`, `prisma db push`는 DB를 초기화하거나 기록 없이 바꿀 수 있어 쓰지 않는다. 테스트 DB 대상으로는 설정 파일이 이 명령들을 막는다.

### 3. 테스트

| 명령                               | 무엇을 검사하나                                                                                                                                                     | DB 필요 |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------- |
| `npm run test`                     | API·화면 단위 테스트                                                                                                                                                | 아니요  |
| `npm run test:db`                  | 실제 PostgreSQL에서 테이블·제약·관계·금액(bigint)·날짜 처리, 인증·프로필·프로젝트·지원·선정·알림·모집 마감·북마크·추천(동시 요청 포함) API·작업 (`workbridge_test`) | 예      |
| `npm run test:scripts -w apps/api` | DB 준비 PowerShell 스크립트 정적 검사                                                                                                                               | 아니요  |

- DB 테스트는 `workbridge_test`에만 연결한다. 테스트 실행 중에는 개발 DB 연결을 코드가 거부한다.
- DB 테스트는 실행할 때마다 표시를 붙인 테스트용 행만 만들고, 끝나면 그 행만 지운다.

## 인증 (이메일·Google)

| API                                   | 설명                                                                     |
| ------------------------------------- | ------------------------------------------------------------------------ |
| `POST /api/auth/signup`               | 회원가입(이름·이메일·비밀번호·역할 `CLIENT`/`FREELANCER`) 후 바로 로그인 |
| `POST /api/auth/login`                | 이메일 로그인                                                            |
| `POST /api/auth/refresh`              | Refresh Token 쿠키로 Access Token 재발급(새로고침 시 세션 복원)          |
| `POST /api/auth/logout`               | 현재 기기의 Refresh Token 무효화                                         |
| `GET /api/auth/me`                    | 내 정보(`Authorization: Bearer <accessToken>`)                           |
| `GET /api/auth/oauth/google/status`   | Google 로그인 사용 가능 여부만 반환(비밀 없음)                           |
| `GET /api/auth/oauth/google`          | Google 로그인 시작(302)                                                  |
| `GET /api/auth/oauth/google/callback` | Google이 돌려보내는 인가 코드 처리                                       |
| `POST /api/auth/oauth/link`           | 기존 이메일 계정에 Google 연결(비밀번호 확인)                            |
| `PATCH /api/auth/role`                | 최초 Google 가입 후 역할 선택(`CLIENT` / `FREELANCER`)                   |

- Access Token(15분)은 응답 본문으로 받아 브라우저 메모리에만 둔다. Refresh Token(14일)은 `HttpOnly` 쿠키 `wb_rt`로만 오가며, DB에는 해시만 저장된다. Google 로그인 뒤에도 같은 토큰을 쓴다. Google 토큰을 Refresh Token 대신 쓰지 않는다.
- 화면: `/signup`, `/login`, `/oauth/complete`, `/oauth/link`, `/select-role`, `/me`.
- 처음 Google로 가입하면 역할을 고른 뒤 내 프로필로 간다. 상세 프로필은 이 단계에서 요구하지 않는다. 이미 역할이 있으면 바꾸지 못한다.
- 같은 이메일의 계정이 있어도 자동으로 연결하지 않는다. 기존 비밀번호로 확인한 뒤에만 연결한다.
- 환경 변수는 `.env.example`의 '인증', 'Google 로그인' 항목을 본다. `JWT_ACCESS_SECRET`을 비워 두면 개발 서버가 실행마다 임시 키를 만든다(경고 출력). **운영에서는 32자 이상의 키가 없으면 서버가 시작하지 않는다.**
- 상세 명세와 정책 근거: `planning/API_SPEC_v1.md` §3·§3.1·§3.2, `planning/DECISIONS.md` D-64~D-74.

### Google Cloud 설정

Google 로그인 버튼은 `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI`가 모두 있을 때만 동작한다. 없으면 로그인 화면에 설정 안내가 나오고, 임의의 키를 만들어 두지 않는다. Client Secret은 `.env`에만 두고 Git에 커밋하지 않는다.

1. [Google Cloud Console](https://console.cloud.google.com/)에서 프로젝트를 만들거나 고른다.
2. **API 및 서비스 → OAuth 동의 화면**에서 사용자 유형을 외부(테스트)로 두고, 앱 이름과 지원 이메일을 입력한다. 로그인에 쓸 Google 계정을 **테스트 사용자**로 넣는다.
3. **API 및 서비스 → 사용자 인증 정보 → 사용자 인증 정보 만들기 → OAuth 클라이언트 ID**에서 애플리케이션 유형을 **웹 애플리케이션**으로 한다.
4. **승인된 JavaScript 원본**에 `http://localhost:5173` 을 넣는다.
5. **승인된 리디렉션 URI**에 아래 주소를 한 글자도 다르지 않게 넣는다.

   `http://localhost:5173/api/auth/oauth/google/callback`

   로컬 개발 서버(Vite)가 `/api`를 API로 프록시하므로, 브라우저는 `localhost:5173`에 머문 채 콜백 쿠키를 받는다. `localhost:4000`으로 두면 프론트와 쿠키 출처가 달라진다.

6. 발급된 클라이언트 ID와 클라이언트 보안 비밀번호를 프로젝트 루트 `.env`에 적는다.

   ```
   GOOGLE_CLIENT_ID=발급된 클라이언트 ID
   GOOGLE_CLIENT_SECRET=발급된 클라이언트 보안 비밀번호
   GOOGLE_REDIRECT_URI=http://localhost:5173/api/auth/oauth/google/callback
   ```

7. API 서버를 다시 시작한다. `GET /api/auth/oauth/google/status`가 `{ "data": { "enabled": true } }`이면 로그인·회원가입 화면에 **Google로 계속하기**가 나타난다.

## 프로필 (의뢰인·프리랜서)

| API                                     | 권한          | 설명                                                               |
| --------------------------------------- | ------------- | ------------------------------------------------------------------ |
| `GET /api/auth/me`                      | 로그인        | 내 정보·역할별 프로필·완성 여부(`profileCompletion`)               |
| `PATCH /api/users/me`                   | 로그인 + 역할 | 이름·자기소개 수정, `profileImageUrl: null`로 이미지 삭제          |
| `PUT /api/users/me/client-profile`      | 의뢰인        | 회사명·사업 분야(필수), 기타 사업 분야, 웹사이트                   |
| `PUT /api/users/me/freelancer-profile`  | 프리랜서      | 주요 카테고리·기술 스택·경력·시간당 단가(필수), 포트폴리오 주소    |
| `POST /api/uploads/profile-image`       | 로그인 + 역할 | 프로필 이미지 업로드(`multipart/form-data`, 필드 `file`, 5MB 이하) |
| `GET /api/uploads/profile-images/:name` | 공개          | 저장된 프로필 이미지                                               |
| `GET /api/tech-stacks?q=`               | 공개          | 기술 스택 검색                                                     |
| `POST /api/tech-stacks`                 | 로그인 + 역할 | 목록에 없는 기술 스택 추가(같은 이름이 있으면 기존 항목 반환)      |
| `GET /api/meta/options`                 | 공개          | 카테고리·사업 분야 선택지                                          |

- 화면: `/me`에서 기본 정보·프로필 이미지와 역할별 프로필을 보고 수정한다. 프로필을 채우지 않아도 로그인과 다른 화면 이용은 그대로 된다. 필수 항목은 프로젝트 등록·지원 단계에서 요구한다.
- 저장 대상은 항상 로그인한 사용자다. 다른 역할의 프로필은 403 `FORBIDDEN`, 역할을 고르지 않은 사용자는 403 `ROLE_REQUIRED`.
- 시간당 단가는 DB `bigint`라 문자열로 주고받는다(예: `"50000"`).
- 프로필 이미지는 JPG·PNG·WebP만 받는다. 서버가 실제 내용을 확인하고 512px 이하 WebP로 다시 저장하며(위치 정보 등 메타데이터 제거), 파일 이름은 무작위로 만든다. SVG나 이미지로 위장한 파일은 거부한다.
- **이미지 저장 위치:** 지금은 로컬 폴더 `apps/api/uploads/profile-images`(Git 제외, `UPLOAD_DIR`로 변경). 무료 호스팅의 디스크는 재배포 때 지워지므로, 배포 전에 영구 저장소(Supabase Storage 등)를 비용 확인 후 정해야 한다(`planning/DECISIONS.md` D-76).
- 기술 스택 기본 선택지는 `npm run db:seed:tech-stacks -w apps/api`로 넣는다.
- 상세 명세와 정책 근거: `planning/API_SPEC_v1.md` §4·§4.1, `planning/DECISIONS.md` D-75~D-78.

| `GET /api/users/:userId` | 공개 | 다른 사용자가 볼 수 있는 프로필(로그인 없이, 읽기 전용) |

- 화면: `/users/:userId`. 프로젝트 상세의 의뢰인 이름, 내 프로필의 **공개 프로필 보기**에서 들어간다.
- 의뢰인은 회사명·사업 분야·웹사이트·소개, 프리랜서는 주요 분야·경력·기술 스택·포트폴리오·자기소개를 보여 준다. 이름·프로필 이미지(없거나 깨지면 이름 첫 글자)는 공통이다.
- **보여 주지 않는 정보:** 이메일, 비밀번호·로그인 방법, Google 연결 정보, 토큰, 시간당 단가, 가입·수정 시각. 시간당 단가는 공개 범위가 정해지지 않아 비공개로 두었다(D-87 제안).
- 프로필을 덜 채운 사용자는 "작성 중" 안내와 함께 채운 항목만 보인다. 역할을 고르지 않았거나 없는 사용자는 404다.
- 수정은 `/me`에서만 한다. 저장하면 공개 프로필에 바로 반영된다. 조회는 DB를 바꾸지 않는다.
- 상세 명세와 항목별 공개 여부: `planning/API_SPEC_v1.md` §4.2, `planning/DECISIONS.md` D-87~D-89(모두 제안).

## 프로젝트 지원 (프리랜서)

| API                                          | 권한                        | 설명                                                                                |
| -------------------------------------------- | --------------------------- | ----------------------------------------------------------------------------------- |
| `POST /api/projects/:projectId/applications` | 프리랜서 + 완성 프로필      | 지원서 제출. `{ coverLetter, proposedAmount: "2500000", proposedDurationDays: 30 }` |
| `GET /api/me/applications?page=&status=`     | 프리랜서                    | 내 지원 현황(10개씩, 최신 지원순). 삭제된 프로젝트의 지원도 남는다                  |
| `GET /api/applications/:applicationId`       | 작성자 또는 프로젝트 소유자 | 지원 한 건. 그 밖의 사용자는 404                                                    |

- 화면: 프로젝트 상세(`/projects/:id`) 아래 **프로젝트 지원** 영역 → 입력 → 확인 → **지원 확정** → 서버가 성공을 돌려주면 `/me/applications`(헤더 **내 지원 현황**)로 이동한다. 이미 지원했으면 상세에 지원 상태가 보인다.
- 결과 표시: **검토 대기 / 선정됨 / 거절됨**. 거절되면 사유("다른 지원자가 선정되어 자동으로 거절되었습니다.", "의뢰인이 거절했습니다." 등)와 처리일이 보이고, 제출한 금액·기간·자기소개는 그대로 남는다.
- 비로그인은 **로그인하고 지원하기**(로그인 후 같은 상세로 돌아옴), 의뢰인에게는 지원 영역이 없다. 프로필이 미완성이면 남은 항목과 **프로필 완성하러 가기**가 나오고, 저장 후 **하던 작업으로 돌아가기**로 상세에 돌아온다.
- 서버 확인 순서: 로그인 → 역할 선택 → 프리랜서 → 필수 프로필 → 프로젝트(없음·삭제·취소는 404) → 실제 모집 상태 → 중복 → 입력값. 모집 상태는 저장된 값이 아니라 오늘 날짜(KST)로 계산하므로, 마감일 다음 날 0시부터는 저장값이 "모집 중"이어도 지원이 거부된다(409).
- 같은 프로젝트에는 한 번만 지원할 수 있다(409 `ALREADY_APPLIED`, 동시에 보내도 1건). 지원서 수정·철회는 없다.
- 지원자가 있으면 의뢰인은 예산·마감일을 바꿀 수 없고, 프로젝트를 삭제하면 대기 중인 지원은 "프로젝트 삭제"로 거절 처리된다.
- 모집이 마감되면(의뢰인의 수동 마감 또는 마감일 경과) 대기 중인 지원은 "모집이 마감되어 자동으로 거절되었습니다."로 바뀐다. 결과는 알림으로도 온다(아래 **알림**).
- 상세 명세와 정책 근거: `planning/API_SPEC_v1.md` §7·§7.1, `planning/ERD_v1.md` §7.6, `planning/DECISIONS.md` D-90~D-94(모두 제안).

| API                                                       | 권한            | 설명                                                                                    |
| --------------------------------------------------------- | --------------- | --------------------------------------------------------------------------------------- |
| `GET /api/projects/:projectId/applications?page=&status=` | 프로젝트 소유자 | 지원자 목록(10개씩, 최신 지원순). 지원자 공개 프로필 요약, 상태별 개수(`counts`) 포함   |

- 선정 확인에서 "이 지원자를 선정하면 다른 대기 지원은 자동으로 거절됩니다."를 보여 준다. 요청 중에는 버튼이 잠기고, 서버가 성공을 돌려준 뒤에만 결과("다른 대기 지원 N건은 자동으로 거절되었습니다.")를 띄운다.
- 선정·거절은 실제 모집 중(마감일 당일 23:59 KST까지)에만 된다. 한 프로젝트에서 한 명만 선정할 수 있고, 동시에 눌러도 한 건만 성공한다(프로젝트 행 잠금 + DB 부분 UNIQUE 인덱스).
- 선정 후에는 새 지원·추가 선정·거절·수정·삭제가 막힌다. 지원서의 제안 금액은 계약 금액이 아니며, 합의 금액·계약·전자 서명·결제는 다음 단계다.
- 선정·거절 결과는 지원자에게 알림으로 간다(아래 **알림**).
- 상세 명세와 정책 근거: `planning/API_SPEC_v1.md` §8·§8.1, `planning/ERD_v1.md` §7.7, `planning/DECISIONS.md` D-95~D-98(모두 제안).

## 모집 마감 (수동·자동)

| API                                   | 권한            | 설명                                                                                 |
| ------------------------------------- | --------------- | ------------------------------------------------------------------------------------ |
| `POST /api/projects/:projectId/close` | 프로젝트 소유자 | 수동 마감(STAT-01). 실제 모집 중일 때만. 응답에 `rejectedCount`·`notifiedCount` 포함 |

- 화면: **내 프로젝트** 각 항목 또는 프로젝트 상세 **프로젝트 관리**의 **모집 마감** → 확인 → **마감 확인**. 서버가 성공을 돌려준 뒤에만 "모집을 마감했습니다. 검토 대기 지원 N건을 자동으로 거절했습니다. 지원자 M명에게 마감 알림을 보냈습니다."를 띄운다. 버튼은 실제 모집 중일 때만 보인다.
- 마감과 함께, 같은 트랜잭션에서 대기 지원 전원이 `REJECTED(PROJECT_CLOSED)`가 되고 그 프로젝트 지원자 전원에게 알림 ⑤가 만들어진다. 이미 선정·거절된 지원의 상태는 바꾸지 않는다. 모집 예정·이미 마감·계약 대기 이후·취소 프로젝트는 409, 남의 프로젝트는 404.
- **자동 마감**: 마감일 다음 날 00:00(KST)이 지나면 같은 처리를 한다. 시작일이 된 모집 예정 프로젝트는 모집 중으로 바꾼다. 조회(GET) 요청은 DB를 바꾸지 않는다(화면의 상태는 날짜로 계산해 보여 준다).
  - API 서버(`npm run dev:api`, `npm start -w apps/api`)가 켜져 있으면 서버 안에서 **시작 즉시 1회 + `RECRUIT_SYNC_INTERVAL_MS`(기본 60000ms = 1분)마다** 실행한다. 서버가 꺼져 있던 동안 지난 마감은 다시 켤 때 처리된다. 실행이 겹치면 건너뛴다. 프로젝트마다 별도 트랜잭션이라 한 건이 실패해도 나머지는 처리되고, 실패한 건은 다음 실행에서 다시 시도한다.
  - `RECRUIT_SYNC_INTERVAL_MS`: 비우면 60000, `0`이면 서버 안 작업을 끈다. 5000~86400000(ms)만 허용한다.
  - 서버 밖에서 한 번 실행: `npm run job:sync-project-status -w apps/api`(개발 DB) 또는 `... -- --target=test`(테스트 DB). 결과를 JSON으로 출력하고, 실패한 프로젝트가 있으면 종료 코드 1. 여러 번·동시에 실행해도 결과는 같다.
- 배포 시: 현재 배포 환경이 없어 운영 스케줄러는 설치하지 않았다. 서버가 잠들 수 있는 호스팅(무료 플랜 등)에서는 서버 안 작업이 멈추므로, 호스팅의 cron/스케줄러에서 위 명령을 주기적으로 실행하도록 연결해야 한다(D-99 제안).
- 상세 명세와 정책 근거: `planning/API_SPEC_v1.md` §9·§9.1, `planning/DECISIONS.md` D-99~D-102(모두 제안).

## 프로젝트 취소

| API                                    | 권한            | 설명                                                                                                  |
| -------------------------------------- | --------------- | ----------------------------------------------------------------------------------------------------- |
| `POST /api/projects/:projectId/cancel` | 프로젝트 소유자 | 계약 체결 전 취소(STAT-02). 응답에 `rejectedCount`(자동 거절한 대기 지원 수)·`keptAcceptedCount` 포함 |

- 취소할 수 있는 상태: 모집 예정·모집 중·모집 마감·계약 대기(체결 전). 작업 중·완료는 409("정상 완료 또는 환불 절차"), 이미 취소된 프로젝트도 409. 삭제(소프트 딜리트)와 다른 동작이다.
- 화면: **내 프로젝트** 항목 또는 상세 **프로젝트 관리**의 **프로젝트 취소** → 확인 창(검토 대기 N건이 자동 거절된다는 안내) → **프로젝트 취소 확정**. 서버가 성공한 뒤에만 "프로젝트를 취소했습니다. 검토 대기 지원 N건을 자동으로 거절했습니다."를 띄운다.
- 같은 트랜잭션에서 대기 지원이 `REJECTED(PROJECT_CANCELLED)`가 된다. 이미 거절된 지원은 그대로, **선정된 지원은 남기고** 프리랜서 화면에 "선정됐지만 프로젝트가 취소되어 계약이 진행되지 않습니다"로 보인다. 중간에 실패하면 전부 되돌린다.
- 취소 알림은 보내지 않는다(필수 5종에 없고, 마감 알림으로 보내면 문구가 틀린다). 프리랜서는 **내 지원 현황**에서 '취소' 표시를 본다.
- 취소된 프로젝트는 검색·추천·북마크 목록에서 빠지고(북마크 기록은 남음), 상세는 소유자와 그 프로젝트 지원자만 볼 수 있다. 자동 마감 작업이나 조회로 다시 모집 중이 되지 않는다.
- 계약 기능이 아직 없어 "체결 후 취소 불가"는 확인 함수 자리만 있다(계약 단계에서 연결).
- 상세 명세와 정책 근거: `planning/API_SPEC_v1.md` §9.2, `planning/DECISIONS.md` D-109~D-113(모두 제안).

## 헤더·확인 창

- 메뉴는 로그인 상태별로 다르다. 비로그인: 프로젝트 찾기·로그인·회원가입. 의뢰인: 프로젝트 찾기·프로젝트 등록·내 프로젝트·알림·내 프로필·로그아웃. 프리랜서: 프로젝트 찾기·내 지원 현황·내 북마크·알림·내 프로필·로그아웃. 역할을 고르기 전: 프로젝트 찾기·역할 선택·로그아웃. 새로고침 후 로그인 상태를 확인하는 동안에는 계정 메뉴를 비워 둔다.
- 화면 너비 900px 이하에서는 **메뉴** 버튼으로 펼친다(알림 종은 항상 보임). 다른 화면으로 가거나 Escape를 누르면 닫힌다.
- 삭제·모집 마감·프로젝트 취소·지원자 선정·거절은 같은 확인 창을 쓴다. 열리면 "취소/돌아가기"에 포커스가 가고, Tab은 창 안에서만 돌며, Escape로 닫으면 누른 버튼으로 포커스가 돌아간다. 요청 중에는 두 번 누를 수 없다.
- 정책 근거: `planning/USER_FLOWS.md` §8.1, `planning/DECISIONS.md` D-114(제안).

## 알림

| API                                             | 권한          | 설명                                                                     |
| ----------------------------------------------- | ------------- | ------------------------------------------------------------------------ |
| `GET /api/notifications?page=&unreadOnly=`      | 로그인 + 역할 | 내 알림(20개씩, 최신순)과 `unreadCount`. 조회만으로는 읽음 처리하지 않음 |
| `GET /api/notifications/unread-count`           | 로그인 + 역할 | 읽지 않은 알림 수                                                        |
| `PATCH /api/notifications/:notificationId/read` | 본인          | 한 건 읽음(다시 보내도 같음). 남의 알림은 404                            |
| `PATCH /api/notifications/read-all`             | 본인          | 내 알림 모두 읽음. `updatedCount`                                        |

| 알림        | 언제                  | 받는 사람               | 누르면                    |
| ----------- | --------------------- | ----------------------- | ------------------------- |
| ① 새 지원   | 지원 제출             | 의뢰인                  | 프로젝트 상세 지원자 관리 |
| ② 선정      | 선정                  | 선정된 프리랜서         | 내 지원 현황              |
| ③ 자동 거절 | 다른 지원자 선정      | 대기였던 프리랜서 각각  | 내 지원 현황              |
| ④ 거절      | 직접 거절             | 해당 프리랜서           | 내 지원 현황              |
| ⑤ 모집 마감 | 수동 마감·마감일 경과 | 그 프로젝트 지원자 전원 | 내 지원 현황              |

- 화면: 머리글 종 아이콘(읽지 않은 수 배지, 30초마다·창으로 돌아올 때 갱신) → `/notifications`. 알림을 누르면 읽음 처리가 성공한 뒤 관련 화면으로 이동하고, **모두 읽음**으로 한 번에 읽는다. 실시간 서버는 없어 새 알림은 최대 약 30초 늦게 보인다.
- 알림은 상태 변경(지원·선정·거절·마감)과 같은 DB 트랜잭션에서 만든다. 알림 저장이 실패하면 그 동작도 취소된다. 같은 이벤트는 `event_key` UNIQUE로 한 번만 만들어진다.
- 알림에는 이름·프로젝트 제목·결과만 담고, 자기소개·금액·이메일·토큰은 넣지 않는다. 이동 경로는 서비스 내부 경로(허용 목록)만 쓰며 DB CHECK 제약으로도 막는다.
- 금액 합의·계약 서명·결제·납품 등 선택 알림은 아직 없다.
- 상세 명세와 정책 근거: `planning/API_SPEC_v1.md` §10·§10.1, `planning/ERD_v1.md` §7.8, `planning/DECISIONS.md` D-103·D-104(제안).

## 북마크·추천 프로젝트

| API                                            | 권한     | 설명                                                                                           |
| ---------------------------------------------- | -------- | ---------------------------------------------------------------------------------------------- |
| `PUT /api/projects/:projectId/bookmark`        | 프리랜서 | 북마크 저장. 이미 있어도 204. 삭제·취소·없는 프로젝트는 404. 프로필 완성은 필요 없다           |
| `DELETE /api/projects/:projectId/bookmark`     | 프리랜서 | 북마크 해제. 없어도 204. 본인 북마크만                                                         |
| `GET /api/me/bookmarks?page=`                  | 프리랜서 | 내 북마크(10개씩, 최근 저장순). 삭제·취소된 프로젝트는 빠지고, 상태는 오늘(KST) 기준           |
| `GET /api/projects/:projectId/recommendations` | 공개     | 비슷한 모집 중 프로젝트 최대 4개(같은 카테고리 → 겹치는 기술 스택 수 → 최근 등록순). DB 읽기만 |

- 화면: 프로젝트 상세 머리말 아래 **☆ 북마크하기 / ★ 북마크됨**(프리랜서), 비로그인은 **로그인하고 북마크하기**(로그인 후 같은 상세로 복귀), 의뢰인에게는 없다. 헤더 **내 북마크**(`/me/bookmarks`)에서 다시 찾아보고 해제한다. 모집 중이고 아직 지원하지 않은 프로젝트에만 **지원하러 가기**가 보인다.
- 상세 맨 아래 **이 프로젝트와 비슷한 모집 중 프로젝트**: 같은 카테고리이거나 필요 기술 스택이 겹치는 프로젝트와 추천 이유. AI·외부 서비스·임베딩은 쓰지 않는다.
- 프로젝트가 삭제·취소돼도 북마크 기록은 지우지 않고 목록에서만 뺀다. 로그아웃하면 브라우저에 남은 북마크·지원 현황·내 프로젝트·상세 캐시를 지운다.
- 상세 명세와 정책 근거: `planning/API_SPEC_v1.md` §6.2·§11.1, `planning/ERD_v1.md` §7.9, `planning/DECISIONS.md` D-105~D-108(제안).
